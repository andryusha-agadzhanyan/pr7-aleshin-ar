Базы данных для индустриальных задач.
ООП в Java: классы, объекты, инкапсуляция и заказ оборудования.

Приложение формирует заказ сотрудника из товаров и количеств. Повторный id
объединяется с существующей позицией; подтверждённый заказ менять нельзя.
Сумма пересчитывается из текущих позиций при каждом вызове total().

## Сборка и запуск

Нужен JDK 17 или новее. Проверено OpenJDK 17.0.20. Сторонних библиотек,
Maven, Stream API, лямбд и method references нет.

Linux/macOS:

~~~bash
bash run_selfcheck.sh
~~~

Windows:

~~~bat
run_selfcheck.bat
~~~

Скрипты переходят в свой каталог, компилируют все семь Java-файлов и передают
аргументы в SelfCheck. На Windows включается кодировка UTF-8.
Вручную из корня проекта:

~~~bash
mkdir out
javac -encoding UTF-8 -d out src/ru/edu/pr04/Product.java src/ru/edu/pr04/Employee.java src/ru/edu/pr04/OrderItem.java src/ru/edu/pr04/Order.java src/ru/edu/pr04/OrderStatus.java src/ru/edu/pr04/OrderService.java src/ru/edu/pr04/SelfCheck.java
java -cp out ru.edu.pr04.SelfCheck
~~~

Если out уже существует, повторно создавать его не нужно. Если javac не найден,
нужно установить JDK и добавить его bin в PATH.

Итог обычного запуска:

~~~text
UNIT: 53 PASS, 0 FAIL
DATA: 28 PASS, 0 FAIL
TOTAL: 81 PASS, 0 FAIL
~~~

Проверки unit/01–18 соответствуют обязательным сценариям методички.
Unit/19–20 проверяют часть А, unit/21–22 — часть Б. Остальные проверки:
границы категорий, неверные данные, удаление, повторное подтверждение,
защита списка и его позиций. Успех возвращает код 0, FAIL — код 1,
неверные аргументы запуска — код 2.

## Вариант 3

Часть А: в Order.confirm добавлена проверка total() > CONFIRM_LIMIT.
CONFIRM_LIMIT = 500000.0. Ровно 500000 допускается; превышение на копейку
отклоняется через IllegalStateException. При отказе заказ остаётся DRAFT.
Пустой заказ и повторное подтверждение по-прежнему запрещены.

Часть Б: нестатический public String addTotalCategory(Order order) в OrderService.

| Сумма | Категория |
| --- | --- |
| меньше 10000 | малая |
| от 10000 до 100000 включительно | средняя |
| больше 100000 и до 500000 включительно | крупная |
| больше 500000 | крупнейшая |

В PDF граница 100000 пересекается в двух диапазонах. Здесь она относится
к средней категории; это решение явно закреплено в проверках.
Пустой заказ имеет малую категорию, но его подтверждение запрещено.

## Правила предметных классов

- Product: id/name не null и не blank; цена конечная и больше 0.
- OrderItem: product не null, количество 1–100 включительно.
- increase принимает положительный delta, проверяет верхнюю границу до сложения
  и вызывает setQuantity. Ошибка не меняет прежнее количество.
- Order: employee не null; используется Objects.requireNonNull.
- addProduct сначала проверяет DRAFT, затем товар и количество. При повторе id
  увеличивается количество, сохраняются первоначальные название и цена товара.
- removeProduct удаляет найденную позицию по id. Отсутствующий id — без изменений;
  null/blank — IllegalArgumentException.
- total суммирует price * quantity; отдельного изменяемого поля total нет.
- addProduct/removeProduct/confirm после подтверждения дают IllegalStateException.
- getItems возвращает List.copyOf списка копий OrderItem. Изменить состав списка
  нельзя; increase у выданной позиции не меняет внутренний заказ.
- Employee — исходный record, OrderStatus — исходный enum DRAFT/CONFIRMED.

Используется double по заготовке. В проверках сумм допуск 0.000001 учитывает
представление дробей; проверка лимита в confirm использует строгое > без допуска.

## Интерактивный режим

После сборки:

~~~bash
java -cp out ru.edu.pr04.SelfCheck --interactive
~~~

Либо со сборкой: bash run_selfcheck.sh --interactive / run_selfcheck.bat --interactive.

| Команда | Действие |
| --- | --- |
| add;id;name;price;quantity | добавить или объединить товар |
| id;name;price;quantity | то же добавление без слова add |
| remove;id | удалить позицию |
| total, category, show | показать состав в числах, сумму, статус и категорию |
| confirm | подтвердить заказ с проверками |
| new | создать другой пустой заказ |
| exit или пустая строка | завершить ввод |

После успешной команды выводятся positions, total, status, category.
После ошибки можно вводить следующую команду. Конец входного потока тоже завершает
программу. Регистр команд важен, пробелы по краям полей запрещены;
внутри названия товара пробелы допустимы.

~~~text
add;M01;Monitor;10000;2
M01;Monitor;10000;3
add;L01;Limit;450000;1
confirm
~~~

Получится 2 позиции, сумма 500000.00, статус CONFIRMED и категория «крупная».
Полные входные строки и фактический вывод примера сохранены в results/.

## Проверки из CSV

По умолчанию читается data/sample.csv. Для другого файла без перекомпиляции:

~~~bash
java -cp out ru.edu.pr04.SelfCheck --data data/my_cases.csv
~~~

Проверки методов также выполняются. Формат строки:
productId;name;price;quantity;expected.
Заголовок, пустые строки и строки с # в начале пропускаются.
Поля разделяются точкой с запятой; пробелы по краям полей не исправляются.
Неверное число, цена или количество дают ожидаемый SKIP и не меняют заказ.

Примеры ожиданий:

- OK:qty=2 — новая позиция с количеством 2.
- OK:merged,qty=3 — повтор объединён, итоговое количество 3.
- merged — объединение без проверки точного количества.
- SKIP:price must be > 0 — ошибка с указанным началом сообщения.
- SKIP — любая IllegalArgumentException входных данных.
- ERROR:IllegalStateException — ошибка состояния.
- ERROR — любая из этих двух ошибок.

Ожидание должно совпасть с фактическим результатом; неверное ожидание,
нарушенная структура файла или пустой набор проверок дают FAIL.

Итоги можно проверить строкой из приложения А:

~~~text
TOTAL;positions=9;sum=431940.00
~~~

Для варианта добавлены необязательные поля category и confirm:

~~~text
TOTAL;positions=10;sum=500000.00;category=крупная;confirm=OK
TOTAL;positions=11;sum=500000.01;category=крупнейшая;confirm=ERROR:IllegalStateException
~~~

confirm проверяется на копии заказа: текущий заказ CSV остаётся DRAFT,
поэтому следующие строки могут продолжать его формирование.
Успешное пробное подтверждение не означает подтверждение основного CSV-заказа.

В sample.csv сохранены 11 строк товаров приложения А с исправлением ожидания
для количества 51: ограничение 50 относилось к варианту 1. Для варианта 3 базовый
итог равен 9 позициям и 431940.00. Далее добавлены четыре строки варианта,
девять собственных ошибочных случаев и четыре проверки TOTAL в разных точках.

## Состав проекта

- src/ru/edu/pr04/ — семь файлов исходной заготовки с завершённой логикой.
- data/sample.csv — данные с ожидаемыми результатами.

в начале PDF — несогласованность материалов. Метод validateForConfirm
с исходной диаграммы удалён, как предписано PDF; подтверждение выполняет Order.

а не по сокращённой таблице Word с неопределённым параметром 20.
